## 들어가며

코드를 보면 어느 정도 해석은 되는데, 막상 직접 작성하려고 하면 막막한 경험이 있나요?

그 이유는 대부분 **"코드를 어떻게 시작하고 연결해가는가"** 에 대한 사고 흐름이 없기 때문이에요.

이 글은 문제를 보고 코드를 작성하기까지의 **사고 흐름을 단계적으로** 보여줍니다. 어려운 개념보다 **직관적인 이해** 를 먼저 챙길게요.

---

## 예제 문제

> "숫자 리스트에서 가장 많이 등장한 숫자를 반환하라"
>
> `[3, 1, 3, 2, 3]` → `3`

---

## 1단계 — 입출력 계약 파악

코드를 생각하기 전에, 딱 이것만 파악하세요:

> **무엇이 들어오고 → 무엇이 나가야 하는가?**

- 입력: 숫자 리스트 `[3, 1, 3, 2, 3]`
- 출력: 가장 많이 나온 숫자 `3`

이것만 정리해도 함수 뼈대가 자동으로 나옵니다:

```python
def most_frequent(nums):

    return
```

---

## 2단계 — 손으로 직접 풀기

머릿속이나 코드로 바로 가지 말고, 손으로 먼저 풀어보세요.

> **내가 사람이라면 이 문제를 어떻게 푸는가?**

- 3이 몇 번? → 3번
- 1이 몇 번? → 1번
- 2가 몇 번? → 1번
- → **3이 제일 많다**

이 손풀기 절차가 곧 코드의 뼈대가 돼요.

---

## 3단계 — 브루트 포스 (직관 그대로)

손으로 푼 절차를 코드로 그대로 옮깁니다. 완벽하지 않아도 괜찮아요.

```python
def most_frequent(nums):
    max_count = 0
    result = None

    for x in nums:          # 각 숫자를 기준으로
        count = 0
        for y in nums:      # 전체를 다시 훑으며
            if x == y:
                count += 1  # 몇 번 나오는지 셈
        if count > max_count:
            max_count = count
            result = x

    return result
```

머릿속으로 추적해보면:

```
x=3: [3,1,3,2,3] 훑음 → count=3 → max_count=3, result=3
x=1: [3,1,3,2,3] 훑음 → count=1
x=2: [3,1,3,2,3] 훑음 → count=1
→ return 3  ✓
```

동작은 맞아요. 하지만 리스트를 여러 번 반복해서 훑고 있어요.

---

## 4단계 — 낭비 찾기

브루트 포스를 보면서 스스로에게 질문을 던집니다:

> **"이 코드에서 반복하는 일 중에, 불필요한 게 있는가?"**

- 3 셀 때 → 리스트 전체 훑음
- 1 셀 때 → 리스트 전체 **또** 훑음
- 2 셀 때 → 리스트 전체 **또또** 훑음

**"리스트를 여러 번 반복해서 훑고 있다" ← 낭비**

---

## 5단계 — 최적화 아이디어

낭비를 발견했으면 이렇게 질문합니다:

> **"한 번만 훑으면서, 지나갈 때 바로 기록하면 되지 않나?"**

기록할 때 두 가지 정보가 필요해요:

- "어떤 숫자가" → "몇 번 나왔는지"

이 두 정보를 쌍으로 묶어서 관리하는 것이 바로 **딕셔너리** 예요.

### 딕셔너리란?

딕셔너리는 `key : value` 형태로 두 정보를 쌍으로 묶어서 관리해요.

```python
{ key : value }
#  ↑       ↑
# "무엇이" "어떤 값"
```

이번 문제에서는:

```python
count = { 3:3, 1:1, 2:1 }
#         ↑  ↑
#        key value
#       숫자 : 등장횟수
```

> 딕셔너리를 쓸 타이밍은 이때예요:
>
> **"두 정보를 연결해서 기억해야 할 때"**

---

## 6단계 — 최적화 코드

```python
def most_frequent(nums):

    # 숫자(key) : 발생횟수(value) 쌍으로 관리할 딕셔너리
    # 예) { 3:3, 1:1, 2:1 } 형태로 채워질 것
    count = {}

    for num in nums:              # 리스트를 딱 한 번만 훑음
        if num not in count:      # 처음 보는 숫자면 (없으니까 먼저)
            count[num] = 1        # 1로 시작
        else:                     # 이미 있는 숫자면
            count[num] += 1       # 그 key의 횟수를 1 증가

    return max(count, key=count.get)  # 횟수가 가장 큰 key 반환
```

채워지는 과정:

```
nums = [3, 1, 3, 2, 3]

num=3 → 처음 등장 → count = {3:1}
num=1 → 처음 등장 → count = {3:1, 1:1}
num=3 → 이미 있음 → count = {3:2, 1:1}
num=2 → 처음 등장 → count = {3:2, 1:1, 2:1}
num=3 → 이미 있음 → count = {3:3, 1:1, 2:1}

→ max → 3  ✓
```

### 코드 핵심 포인트

**`count = {}`**
빈 딕셔너리를 먼저 선언. 기록할 빈 표를 꺼내놓는 것.

**`num not in count`**
"num이 count의 key 중에 없는가?" 를 묻는 것.
현재 상황이 빈 상태에서 시작하니, 없는 경우를 먼저 처리하는 게 더 직관적.

**`count[num] += 1`**
key가 num인 곳의 value를 1 증가.
`count[3] += 1` 이면 key=3의 value가 1 늘어남.

**`max(count, key=count.get)`**
"count 딕셔너리에서, value가 가장 큰 것의 key를 가져와라"

## 복습 — 변형 문제

> "리스트에서 가장 적게 등장한 숫자를 반환하라"
>
> `[3, 1, 3, 2, 3, 1]` → `2`

딕셔너리 구조는 동일해요:

```python
count = { 숫자(key) : 발생횟수(value) }
count = { 3:3, 1:2, 2:1 }
```

코드에서 바뀌는 건 딱 한 글자:

```python
def least_frequent(nums):

    count = {}

    for num in nums:
        if num not in count:
            count[num] = 1
        else:
            count[num] += 1

    return min(count, key=count.get)  # max → min 으로만 변경
#          ↑
#      이것만 바뀜
```

코드 구조를 이해하면, 문제가 바뀌어도 **어디만 바꾸면 되는지** 바로 보여요.

## 전체 사고 흐름 요약

```
1. 입출력 계약 파악        → 함수 뼈대 작성
         ↓
2. 손으로 직접 풀기        → 알고리즘 방향 결정
         ↓
3. 브루트 포스 작성        → 일단 동작하는 코드
         ↓
4. 낭비 찾기               → "같은 걸 또 훑고 있네?"
         ↓
5. 최적화 아이디어         → "지나가면서 바로 기록하자"
         ↓
6. 자료구조 선택           → 두 정보를 연결 → 딕셔너리
```

## 마치며

처음부터 최적 풀이를 떠올리려 하면 오히려 막혀요.

**직관 → 브루트 포스 → 낭비 발견 → 최적화**

이 흐름이 자연스러워지면, 새 문제를 봤을 때 어디서 시작해야 할지 보이기 시작해요.

> 코딩은 암기가 아니라 **사고 흐름** 이에요.
